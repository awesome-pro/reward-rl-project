# RewardForge first-experiment data card

## Purpose

This corpus supports a CPU-only, offline study of **executable reward
reliability** for Python code-generation benchmarks. It does not train a model
and does not evaluate model capability. The unit of analysis is a
`(task, candidate, test)` execution result.

## Construction

1. Parse each HumanEval+/MBPP+ suite into individual test cases.
2. Materialize the expected value from the suite's `results` list or its
   `ref_func`; quarantine cases whose expected value exceeds 16,384 characters.
3. Validate every candidate bank/audit case against the canonical solution
   **twice**; drop cases that fail, raise, time out, or disagree between runs.
4. Deduplicate cases by argument tuple and remove cases whose arguments already
   appear in the base tests.
5. Split the remaining validated cases deterministically (seed
   `20261109`) into a **candidate bank** (80 HumanEval / 53 MBPP cases per task)
   and a **private audit** set (same caps, disjoint).
6. Select dev and eval tasks by a stable hash of the seed and task ID:
   **80 dev + 82 eval** HumanEval, **80 dev + 80 eval** MBPP.
7. Build the candidate table from pinned release artifacts, preserving
   generator attribution and code hashes (identical code is not collapsed).

Base tests are the task's weak-reward tests: original HumanEval `check()` or
the EvalPlus MBPP+ base `test_list` plus its `test_imports`. They are not part
of the bank/audit split. Because audit cases deliberately exclude base-overlap
inputs, a base-fail candidate that passes the sampled audit is **not** proof
that the base test was wrong; the 17/412 figure is an upper bound on base-test
false rejection, not a measured false-rejection rate.

## Exclusions

Nine tasks were excluded before splitting because they had too few valid
additional cases or an inconsistent canonical/test contract:

`HumanEval/32`, `HumanEval/39`, `Mbpp/455`, `Mbpp/583`, `Mbpp/596`,
`Mbpp/635`, `Mbpp/734`, `Mbpp/762`, `Mbpp/793`.

The full reasons and per-task validation statistics are in
[`data/processed/splits.json`](data/processed/splits.json). HumanEval/32's
custom test calls `_poly(*candidate(*inp), inp)` although the canonical
`find_zero` returns a scalar; Mbpp/596's canonical output disagrees with its
expected value. These are quarantined rather than repaired.

## Intended use

- Measuring base-vs-audit reward disagreement on natural candidates.
- Replaying budgeted test-selection policies with measured per-test costs.
- Auditing verifier behavior; building a reusable public/private test split.

## Not intended for

- Claims that a candidate is mathematically correct.
- Training on evaluation-suite outcomes (the private audit is never used by the
  policy).
- Adversarial sandbox evaluation without an OS/container boundary; see the
  security limitations in the README.
- Redistribution without checking upstream licenses.

## Known limitations

- The audit label is a **suite-based gold proxy**, not proof of correctness.
- Bank and audit sets are samples of the enhanced suite; detection power is
  finite and the audit label can miss a defect.
- The candidate distribution is fixed public output, not a fresh RL policy.
- Test execution costs are host-specific; the measured medians are reported
  with the experiment.
- The 32 eval base-pass/audit-fail candidates are just above the
  pre-registered minimum, so confidence intervals are wide.
